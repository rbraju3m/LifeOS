# 10. Database Schema

### 10.0 Conventions (apply to every table unless stated)
- Engine InnoDB, charset `utf8mb4`, collation `utf8mb4_0900_ai_ci`. ULID columns use `CHAR(26) CHARACTER SET ascii COLLATE ascii_bin`.
- **[STD]** = the table has `id CHAR(26) PK NOT NULL` (ULID, generated by the app), `created_at DATETIME(3) NOT NULL`, `updated_at DATETIME(3) NOT NULL`.
- **[SD]** = also has `deleted_at DATETIME(3) NULL` with an index (soft delete → Trash, purged after 30 days).
- **[OWN]** = owned content columns: `space_id CHAR(26) NOT NULL FK→spaces.id ON DELETE CASCADE`, `created_by CHAR(26) NULL FK→users.id ON DELETE SET NULL` (nullable so content in shared spaces survives when the creator's account is deleted; in a personal space the whole space is purged anyway), and `visibility ENUM('space','private') NOT NULL DEFAULT 'space'`.
  - In a personal space `visibility` makes no difference because only the owner is a member.
  - In a family space, `private` means only `created_by` can see the item (owners/admins **cannot** override this).
- FKs are named `fk_<table>_<col>`. Every FK column is indexed.
- Booleans are `TINYINT(1) NOT NULL DEFAULT 0`.
- Ownership rule (applies everywhere): **authorization derives from `space_id` membership + role + `visibility` + `created_by`**, never from client input.

### 10.3 Tags module
**tags** [STD][OWN-lite: `space_id`, `created_by`] — `name VARCHAR(50) NOT NULL`, `color CHAR(7) NULL`. Unique `(space_id, name)`.
Pivot tables use explicit per-module tables instead of a polymorphic `taggables`, so FKs and cascades work and authorization joins stay simple:
- `task_tag(task_id, tag_id)`
- `note_tag(note_id, tag_id)`
- `record_tag(record_id, tag_id)`

Each has a composite PK, both FKs CASCADE, and a reverse index `(tag_id)`. The service layer checks that the tag and the item belong to the same space.

**tasks** [STD][SD][OWN]

| Field | Type | Null | Default | Notes |
|---|---|---|---|---|
| task_list_id | CHAR(26) | Y | NULL | FK→task_lists SET NULL; same-space check |
| assignee_user_id | CHAR(26) | Y | NULL | FK→users SET NULL; must be an active member (Phase 5 UI) |
| title | VARCHAR(255) | N | | |
| description | TEXT | Y | NULL | max 10k chars |
| status | ENUM('open','completed','cancelled') | N | 'open' | |
| priority | TINYINT UNSIGNED | N | 0 | 0 none, 1 low, 2 med, 3 high |
| due_date | DATE | Y | NULL | local date (all-day due) |
| due_at | DATETIME(3) | Y | NULL | UTC instant when a time is set |
| timezone | VARCHAR(64) | N | | creator tz at time of save |
| rrule | VARCHAR(500) | Y | NULL | RFC 5545 RRULE (no DTSTART) |
| recurrence_series_id | CHAR(26) | Y | NULL | ULID shared by all instances of a series |
| completed_at | DATETIME(3) | Y | NULL | |
| completed_by | CHAR(26) | Y | NULL | FK→users SET NULL |
| sort_order | INT | N | 0 | |

Indexes: `(space_id, status, due_date)`, `(space_id, status, due_at)`, `(space_id, status, due_sort)`, `(assignee_user_id, status)`, UNIQUE `(recurrence_series_id, due_date)`, `(created_by)`, FULLTEXT `(title, description)`.
`due_sort DATETIME(3)` is a stored generated column, `COALESCE(due_at, TIMESTAMP(due_date,'23:59:59'), '9999-12-31 23:59:59')`, so "sort by due" can use cursor pagination (which cannot page over NULLs). Date-only tasks sort at 23:59 UTC of their date, which can be a few hours off relative to timed tasks that day; the today/overdue views do not use it.
**Trash:** deleting a list moves its tasks that the deleter can see to the Trash with the list's exact `deleted_at`; restoring the list restores exactly those. Other members' private tasks in the list are moved out of it instead. A task restored while its list is still in the Trash comes back outside any list.
CHECK: `due_at IS NULL OR due_date IS NOT NULL` (due_date always holds the local date, which keeps the "today" query simple).
**Recurrence model:** complete-to-generate. Completing an instance with an `rrule` creates the next instance (copying fields, tags and reminder templates) in the same transaction, which is idempotent per `(recurrence_series_id, due_date)`. This is simpler than virtual occurrences and matches how people think about chores.
- The next date is the first occurrence after the current due date that is also on or after today in the task's timezone, so completing a late task does not create a backlog. Occurrences skipped this way count toward `COUNT`; the next instance stores the remaining `COUNT`. The rule is evaluated from the current instance's date, which keeps interval phase (and continues from a date the user moved).
- Timed tasks keep their local time on the new date (DST-safe). The original `created_by` is kept, so a private series stays private.
- The unique `(recurrence_series_id, due_date)` makes generation idempotent: completing again after a reopen returns the existing next instance, and a next instance in the Trash is not recreated. Reopening does not remove an already generated next instance.
- `UNTIL` may be a date or a UTC date-time; only its date is used.

### 10.5 Calendar module

**events** [STD][SD][OWN]

| Field | Type | Null | Default | Notes |
|---|---|---|---|---|
| title | VARCHAR(255) | N | | |
| description | TEXT | Y | NULL | |
| location | VARCHAR(255) | Y | NULL | |
| all_day | TINYINT(1) | N | 0 | |
| starts_at / ends_at | DATETIME(3) | Y | NULL | UTC, set when not all_day |
| start_date / end_date | DATE | Y | NULL | set when all_day (end inclusive) |
| timezone | VARCHAR(64) | N | | wall-clock zone of the series |
| rrule | VARCHAR(500) | Y | NULL | |
| recurrence_until | DATETIME(3) | Y | NULL | UTC end of series (NULL = infinite); derived from rrule for range queries |
| color | CHAR(7) | Y | NULL | |

Generated column `is_recurring TINYINT(1) AS (rrule IS NOT NULL) STORED`.
Indexes: `(space_id, starts_at)`, `(space_id, start_date)`, `(space_id, is_recurring, recurrence_until)`.
Window query = non-recurring rows overlapping the window, UNION recurring rows whose series has not ended before the window.
CHECK: `(all_day=1 AND start_date IS NOT NULL) OR (all_day=0 AND starts_at IS NOT NULL)`.
Expansion: occurrences are expanded **on read** for the requested window (max 92 days per query) in the event's time zone, then converted to UTC. They are never materialised.

**event_exceptions** [STD] — per-occurrence overrides.
- `event_id` FK→events CASCADE, `original_start DATETIME(3) N` (UTC start of the occurrence being overridden; for all-day, midnight of the local date stored as a DATE in `original_date`)
- `original_date DATE Y`, `kind ENUM('cancelled','modified') N`
- Override columns, all nullable: `title`, `description`, `location`, `starts_at`, `ends_at`, `start_date`, `end_date`

Unique `(event_id, original_start, original_date)`.
"Edit this and following" splits the series: the old event gets `UNTIL` and a new event row is created.

### 10.6 Notes module

**subscriptions** [STD]
- `space_id` FK CASCADE, `plan_id` FK RESTRICT
- `status ENUM('active','trialing','past_due','cancelled','expired') N`
- `provider ENUM('none','manual','sslcommerz','bkash','stripe') N 'none'`, `provider_ref VARCHAR(255) Y`
- `starts_at DATETIME(3) N`, `current_period_end DATETIME(3) Y`, `cancelled_at DATETIME(3) Y`

A space with no live subscription resolves to the default plan for its type (`free` or `free_family`).
*Implemented in slice 1.2:* `plans.is_default` + generated unique `default_key` (one default per space type); a `free_family` plan (3 members); `subscriptions.space_id` is ON DELETE **RESTRICT** (MySQL forbids cascading on a column a stored generated column depends on), so purging a space deletes its subscriptions first; the SMS feature is the limit `reminders.sms_per_month` instead of a boolean.

**data_exports** [STD] — `user_id` FK CASCADE, `status ENUM('queued','processing','ready','failed','expired') N`, `storage_key VARCHAR(255) Y` (exports bucket prefix, not in `files`), `size_bytes BIGINT Y`, `expires_at DATETIME(3) Y` (+7 days), `downloaded_at DATETIME(3) Y`. **Idempotency keys:** stored in Redis as `idem:{user}:{key}` with a 24-hour TTL, holding the request hash and response. No table.

### 10.9 Future-phase tables (provisional — final design happens at the start of each phase)
All are [STD][SD][OWN] unless noted. Money is `*_amount_minor` + `currency`.

**Phase 2 ObligationOS**

### 10.10 Relationship & policy explanations
- **1:1:** users ↔ user_preferences; users ↔ personal space (enforced by `personal_owner_key`).
- **1:N:** space → tasks/notes/events/records/files/tags/reminders; task_list → tasks; record → record_fields; event → event_exceptions; reminder → reminder_occurrences; notification → deliveries; plan → plan_prices.
- **M:N:** users ↔ spaces (space_members); tasks/notes/records ↔ tags (per-module pivots); notes/records ↔ files (attachment pivots); plans ↔ features (plan_features).
- **Cross-module:** feature → files via pivots owned by the feature module; any module → reminders via `source_type/source_id` + registry; dashboard/search read through contracts. FKs that cross module boundaries are allowed only *toward* platform tables (spaces, users, files).
- **Personal vs shared data:** determined only by the type of the owning space plus `visibility`. Moving an item between spaces ("share to family") is an explicit, audited `move` action. It re-checks permissions in both spaces and moves attachments and reminders with it. Copying is not offered in the MVP.
- **Audit history:** security and privacy-relevant actions go to `audit_logs`. Content edit history (versioning) is out of scope for the MVP; `updated_at` is enough.
- **Soft deletion:** content [SD] → Trash (30 days) → `PurgeTrash` daily job hard-deletes, which cascades to pivots, cancels reminders and purges file objects. Users can "Delete permanently" from Trash.
- **File references:** never stored as URLs. Only `files.id` is stored; URLs are minted per request (§16).
- **Recurring events:** RFC 5545 RRULE strings, expanded in the stored IANA time zone with `rlanvin/php-rrule` on the backend and `rrule.js` on the frontend for previews. Tasks are complete-to-generate, events are expanded on read with exceptions, and reminders use `next_fire_at` with a forward-only cursor.
- **Time zones:**
  - Instants are stored in UTC.
  - User intent is stored as local wall-clock time plus the IANA zone, so "9 AM every day" stays 9 AM across DST changes.
  - Date-only values stay `DATE`.
  - When a user changes their time zone, they are asked whether to shift existing reminders (default: keep local wall-clock, recompute `next_fire_at`).
  - The tzdata on the server is kept current through OS updates and the PHP `timezonedb` extension.
